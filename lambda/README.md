# JD Dental Lab — Scan Conversion Lambda

S3-triggered AWS Lambda that converts raw intraoral scans (**STL / PLY / OBJ-zip**)
uploaded under `scans/raw/` into small, decimated, **Meshopt-compressed GLB**
files written to `scans/glb/`, so the portal viewer never loads 70–150 MB raw
meshes. It reuses the same pure-Node `convertScan()` core as the app (vendored
here at package time).

- Entry point: [`handler.mjs`](handler.mjs) → exported `handler`
- Conversion core: `convert-scan.mjs` (vendored from `../scripts/convert-scan.mjs`)
- Runtime: **Node.js 22**, **x86_64**, 4096 MB, 300 s timeout
- Bucket: `jdlab-scans-prod-use1` (us-east-1); reads `scans/raw/`, writes `scans/glb/`
- IAM / S3 wiring: [`aws/`](aws/) (trust policy, S3 read/write policy, bucket notification)

> **Build host matters:** the bundle contains a native `sharp`/libvips binary
> (pulled in transitively by `@gltf-transform/functions`), so it **must be built
> on Linux x86_64** — the same platform the function runs on. Build in **AWS
> CloudShell** (or a Linux x86_64 box). A Windows/macOS build ships the wrong-OS
> binary and the function crashes at load. This is why the function is deployed
> as **x86_64**, not arm64.

> `node_modules/`, the vendored `convert-scan.mjs`, and `lambda.zip` are build
> artifacts — **gitignored**, regenerated by `npm run bundle`. Not committed.

## Build + deploy from AWS CloudShell (recommended, step by step)

CloudShell is Linux x86_64, pre-authenticated, and behind no corporate proxy —
the right place to build. Its persistent `$HOME` is only **1 GB**, which
`node_modules` exceeds, so **build in `/tmp`** (roomy, ephemeral) with the npm
cache there too.

Open CloudShell in **us-east-1** and run `export AWS_PAGER=""` first (stops the
pager from swallowing command output).

### 1. Get the three source files into CloudShell

They're tiny — upload via **Actions ▸ Upload file** into a working dir
(e.g. `~/lambda-src/`):

- `handler.mjs` and `package.json` — from this `lambda/` folder
- `convert-scan.mjs` — from the app's `scripts/convert-scan.mjs`

> ⚠️ Upload **this** `lambda/package.json` (6 deps), **NOT** the app's root
> `package.json`. The app's pulls in Next.js/Azure/Drizzle/etc. → ~600 MB
> `node_modules`, which blows the **250 MB unzipped** Lambda limit.

### 2. Install prod deps in /tmp

```bash
rm -rf /tmp/lb && mkdir -p /tmp/lb
cp ~/lambda-src/handler.mjs ~/lambda-src/package.json ~/lambda-src/convert-scan.mjs /tmp/lb/
cd /tmp/lb
npm install --omit=dev --cache /tmp/.npmcache --no-audit --no-fund
du -sh node_modules            # expect ~70 MB
```

`@aws-sdk/client-s3` is provided by the Node 22 runtime, so it's intentionally
NOT a dependency here.

### 3. Verify the mesh loaders are present (gate before zipping)

```bash
ls node_modules/three/examples/jsm/loaders/STLLoader.js
```

### 4. (If needed) trim sharp to linux-x64 only

A fresh minimal install pulls only the linux-x64 binary. If `node_modules/@img`
ever has extra platforms, keep just the two linux-x64 dirs so you stay under the
250 MB limit:

```bash
cd /tmp/lb/node_modules/@img && for d in */; do
  case "$d" in sharp-linux-x64/|sharp-libvips-linux-x64/) ;; *) rm -rf "$d";; esac
done; cd /tmp/lb
```

### 5. Zip (files at archive root) and confirm the loader is inside

```bash
rm -f /tmp/lambda.zip
zip -r /tmp/lambda.zip handler.mjs convert-scan.mjs package.json node_modules >/dev/null
unzip -l /tmp/lambda.zip | grep -c -i STLLoader     # must be > 0
ls -lh /tmp/lambda.zip
```

### 6. Stage in S3 and deploy as x86_64

```bash
aws s3 cp /tmp/lambda.zip s3://jdlab-scans-prod-use1/deploy/lambda.zip
aws lambda update-function-code --function-name jdlab-scan-convert \
  --s3-bucket jdlab-scans-prod-use1 --s3-key deploy/lambda.zip \
  --architectures x86_64 --region us-east-1
aws lambda wait function-updated --function-name jdlab-scan-convert --region us-east-1
```

> Deploy **via S3** (`--s3-bucket/--s3-key`), not `--zip-file` — inline upload
> caps at 50 MB.

> **On a Linux x86_64 machine with the full repo?** Skip the manual upload:
> `cd lambda && npm run bundle` (vendors `../scripts/convert-scan.mjs`, then
> `npm install --omit=dev`), then zip as in step 5. Do **not** build on
> Windows/macOS — wrong-OS `sharp` binary.

## First-time deploy (create the role + function)

Only needed once. `SCAN_BUCKET=jdlab-scans-prod-use1`, `REGION=us-east-1`,
`ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)`.

1. **Build + stage the zip** — do steps 1–5 above, then:
   ```bash
   aws s3 cp /tmp/lambda.zip s3://jdlab-scans-prod-use1/deploy/lambda.zip
   ```
2. **IAM role** (prefix-scoped S3 policy):
   ```bash
   sed -i "s|<SCAN_BUCKET>|jdlab-scans-prod-use1|g" aws/s3-read-write-policy.json
   aws iam create-role --role-name jdlab-scan-convert \
     --assume-role-policy-document file://aws/trust.json
   aws iam attach-role-policy --role-name jdlab-scan-convert \
     --policy-arn arn:aws:iam::aws:policy/service-role/AWSLambdaBasicExecutionRole
   aws iam put-role-policy --role-name jdlab-scan-convert \
     --policy-name scan-s3-rw --policy-document file://aws/s3-read-write-policy.json
   ```
3. **Create the function (x86_64):**
   ```bash
   aws lambda create-function --function-name jdlab-scan-convert \
     --runtime nodejs22.x --handler handler.handler \
     --role arn:aws:iam::$ACCOUNT_ID:role/jdlab-scan-convert \
     --code S3Bucket=jdlab-scans-prod-use1,S3Key=deploy/lambda.zip \
     --memory-size 4096 --timeout 300 --architectures x86_64 --region us-east-1
   ```
4. **Allow S3 to invoke it:**
   ```bash
   aws lambda add-permission --function-name jdlab-scan-convert \
     --statement-id s3invoke --action lambda:InvokeFunction \
     --principal s3.amazonaws.com \
     --source-arn arn:aws:s3:::jdlab-scans-prod-use1 --region us-east-1
   ```
5. **Wire the S3 trigger** (filters `scans/raw/` + `.stl`/`.ply`/`.zip`):
   ```bash
   sed -i "s|<REGION>|us-east-1|g; s|<ACCOUNT_ID>|$ACCOUNT_ID|g" aws/s3-notify.json
   aws s3api put-bucket-notification-configuration --bucket jdlab-scans-prod-use1 \
     --notification-configuration file://aws/s3-notify.json
   ```

## Manual test (no trigger needed)

Since a raw object already exists, invoke the function directly with a synthetic
S3 event — this validates the conversion independently of the trigger:

```bash
cat > /tmp/event.json <<'JSON'
{ "Records":[ { "s3": { "bucket": { "name":"jdlab-scans-prod-use1" },
  "object": { "key":"scans/raw/test.stl" } } } ] }
JSON
aws lambda invoke --function-name jdlab-scan-convert \
  --payload file:///tmp/event.json --cli-binary-format raw-in-base64-out \
  --region us-east-1 /tmp/out.json
cat /tmp/out.json                 # expect {"ok":true,"converted":1}
aws s3 ls s3://jdlab-scans-prod-use1/scans/glb/    # expect test.glb
aws logs tail /aws/lambda/jdlab-scan-convert --follow --format short --region us-east-1
```

## Gotchas (learned the hard way)

- **Build on Linux x86_64 only.** The native `sharp`/libvips binary is
  OS/CPU-specific; a Windows/macOS build → `Cannot find module '…sharp-linux-x64…'`
  at load. Function is deployed **x86_64** to match a CloudShell build.
- **CloudShell HOME is 1 GB** → `node_modules` triggers `ENOSPC`. Build in
  `/tmp` and put the npm cache there (`--cache /tmp/.npmcache`).
- **Use this minimal `package.json`,** not the app's root one — the app's brings
  Next.js/etc. and exceeds the **250 MB unzipped** limit (real build was 606 MB).
- **Deploy via S3** (`--s3-bucket/--s3-key`); `--zip-file` inline caps at 50 MB.
- `export AWS_PAGER=""` so the CLI pager doesn't hijack output.
